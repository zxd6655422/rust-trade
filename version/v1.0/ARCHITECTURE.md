# 架构设计 - 三层服务分离方案

## 核心架构约束（强制遵守）

### 约束1：信号路径唯一性

**信号只能从策略服务发出**，策略服务是系统中唯一的信号源。

```
┌─────────────────────────────────────────────────────────────────┐
│                     信号路径（唯一）                              │
│                                                                  │
│  行情数据 ──▶ 策略服务 ──▶ Buy/Sell 信号 ──▶ 交易执行引擎        │
│                  │                                               │
│                  │ 所有数据（K线、Tick、指标）                      │
│                  │ 都在策略服务内部消化处理                         │
│                  ▼                                               │
│            信号输出（唯一出口）                                    │
└─────────────────────────────────────────────────────────────────┘

❌ 禁止：交易引擎自行从 Tick 数据生成信号
❌ 禁止：任何模块绕过策略服务直接产生交易信号
✅ 唯一：策略服务处理所有数据并输出 Buy/Sell/Hold
```

- 交易引擎只负责：接收信号 → 校验 → 执行 → 记录
- 信号去重由策略服务保证，交易引擎不承担去重职责

### 约束2：持仓风险计算 = 实时交易所数据

**持仓风险计算必须实时从交易所获取真实持仓数据**，不得使用任何缓存或数据库数据。

```
┌─────────────────────────────────────────────────────────────────┐
│                     数据用途分层                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  实时数据源（风险计算）          存储数据源（前端展示）             │
│  ┌─────────────────┐           ┌─────────────────┐              │
│  │ 交易所 API       │           │ PostgreSQL       │              │
│  │ get_positions()  │           │ positions 表     │              │
│  │ get_account()    │           │ trades 表        │              │
│  └────────┬────────┘           └────────┬────────┘              │
│           │                              │                       │
│           ▼                              ▼                       │
│  ┌─────────────────┐           ┌─────────────────┐              │
│  │ RiskEngine       │           │ 监控桌面应用      │              │
│  │ 风控判断          │           │ 持仓/盈亏展示    │              │
│  │ 仓位计算          │           │ 历史回溯         │              │
│  └─────────────────┘           └─────────────────┘              │
│                                                                  │
│  ⚠️ 两套数据绝不混用                                             │
└─────────────────────────────────────────────────────────────────┘
```

- 数据库存储的持仓快照**仅用于前端展示和历史回溯**，不参与任何风险计算
- 风险计算的输入**只能是**：交易所 API 返回的实时持仓 + 实时账户余额

### 约束3：交易信号执行校验链

策略服务发出 Buy/Sell 信号后，交易执行前**必须依次经过以下校验**，任何一步失败则拒绝执行：

```
┌─────────────────────────────────────────────────────────────────┐
│                    信号执行校验链（必须全部通过）                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Step 1: 交易类型校验                                            │
│  ├── 检查配置：是否启用现货交易？是否启用合约交易？                  │
│  └── 不匹配 → Reject("trading type not enabled")                │
│           │                                                      │
│           ▼                                                      │
│  Step 2: 持仓检查                                                │
│  ├── 查询交易所实时持仓                                           │
│  ├── Buy 信号：是否已有该交易对持仓？                              │
│  └── Sell 信号：是否有足够持仓可平？                               │
│           │                                                      │
│           ▼                                                      │
│  Step 3: 未成交订单检查                                           │
│  ├── 是否有同方向挂单未成交？                                      │
│  └── 避免资金被重复占用                                           │
│           │                                                      │
│           ▼                                                      │
│  Step 4: 仓位占比检查                                             │
│  ├── 计算：本次开仓价值 / 账户总余额                               │
│  └── 超过配置阈值 → Reject("position limit exceeded")            │
│           │                                                      │
│           ▼                                                      │
│  ✅ 全部通过 → Allow → 执行下单                                   │
└─────────────────────────────────────────────────────────────────┘
```

## 三层架构

### 整体架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        量化交易系统                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  Layer 1: trading-core (数据采集 + 指标计算 + Redis缓存)  │  │
│  │  ──────────────────────────────────────────────────────── │  │
│  │  • REST 轮询采集 K线数据                                   │  │
│  │  • 计算技术指标 (MA/RSI/MACD)                              │  │
│  │  • 写入 PostgreSQL + Redis                                 │  │
│  │  • HTTP API + WebSocket                                    │  │
│  │  • 无需 API Key，只读操作                                  │  │
│  └───────────────────────────────────────────────────────────┘  │
│                              │                                   │
│                              ▼                                   │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  Layer 2: strategy-service (策略分析 + 信号生成)           │  │
│  │  ──────────────────────────────────────────────────────── │  │
│  │  • 从 PostgreSQL 加载策略实例配置                           │  │
│  │  • 从 Redis 读取指标数据（毫秒级）                          │  │
│  │  • 运行策略逻辑（7种内置策略）                              │  │
│  │  • 信号写入 strategy_signals 表                            │  │
│  │  • WebSocket 推送 + 告警通知                               │  │
│  └───────────────────────────────────────────────────────────┘  │
│                              │                                   │
│                              ▼                                   │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  Layer 3: trading-engine (交易执行)                        │  │
│  │  ──────────────────────────────────────────────────────── │  │
│  │  • 从 strategy_signals 表轮询待执行信号                    │  │
│  │  • 风控检查（持仓数量/金额/杠杆）                           │  │
│  │  • 调用交易所 API 下单（支持多交易所）                      │  │
│  │  • 订单状态同步 + 止损止盈管理                             │  │
│  │  • 持仓同步与对账                                          │  │
│  │  • 需要 API Key，涉及资金操作                              │  │
│  └───────────────────────────────────────────────────────────┘  │
│                              │                                   │
│                              ▼                                   │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │  PostgreSQL + Redis (数据存储 + 缓存)                     │  │
│  └───────────────────────────────────────────────────────────┘  │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 服务间通信

```
trading-core ──写入──▶ Redis (K线 + 指标)
                              │
strategy-service ◀──读取──┘
      │
      ├──写入──▶ PostgreSQL (strategy_signals)
      │
      └──推送──▶ WebSocket (前端)
                              │
trading-engine ◀──轮询──┘
      │
      ├──写入──▶ PostgreSQL (trades, positions, risk_logs)
      │
      └──调用──▶ 交易所 API (下单)
```

**通信方式**：通过数据库（PostgreSQL）和缓存（Redis）解耦，不直接调用。

## SignalPoller 主循环

交易引擎职责最小化，只有一个主循环：**SignalPoller**

```
┌─────────────────────────────────────────────────────────────┐
│                    SignalPoller 主循环                        │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  定时任务：                                                   │
│  ├── 每 5s   轮询 strategy_signals 表 → 执行交易              │
│  ├── 每 5s   检查止损止盈（交易所获取实时价格）                  │
│  ├── 每 30s  检查持仓风控                                      │
│  ├── 每 5min 同步持仓到 RiskEngine                            │
│  └── 每 1h   清理过期信号                                     │
│                                                              │
│  信号执行流程：                                                │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐       │
│  │ 读取信号     │───▶│ 查询市场数据 │───▶│ 校验执行     │       │
│  │ (DB 轮询)   │    │ (交易所API)  │    │ (OrderMgr)  │       │
│  └─────────────┘    └─────────────┘    └─────────────┘       │
└─────────────────────────────────────────────────────────────┘
```

## 核心设计原则

### 1. 职责分离
```
trading-core:      数据采集 + 指标预计算（只读）
strategy-service:  策略分析 + 信号生成（分析）
trading-engine:    交易执行 + 风控（读写）
```

### 2. 风险隔离
```
trading-core 崩溃      → 不影响资金安全
strategy-service 崩溃  → 不影响资金安全
trading-engine 崩溃    → 数据采集继续运行
```

### 3. 安全分层
```
trading-core:      无需 API Key
strategy-service:  无需 API Key
trading-engine:    存储 API Key，权限受限
```

## 故障处理

```
场景 1: trading-core 崩溃
├── strategy-service 继续运行（使用 Redis 缓存数据）
├── trading-engine 继续运行
├── systemd 自动重启 trading-core
└── 数据恢复后自动追上

场景 2: strategy-service 崩溃
├── trading-core 继续运行
├── trading-engine 继续运行（处理已有信号）
├── systemd 自动重启 strategy-service
└── 重启后继续生成信号

场景 3: trading-engine 崩溃
├── trading-core 继续运行
├── strategy-service 继续运行（信号堆积）
├── systemd 自动重启 trading-engine
└── 重启后继续处理信号，对账持仓

场景 4: PostgreSQL 崩溃
├── 所有服务暂停
├── Redis 缓存继续工作
├── 数据库恢复后自动重连
└── 补写丢失的数据

场景 5: Redis 崩溃
├── strategy-service 降级运行（直接读 DB）
├── trading-engine 继续运行
├── Redis 恢复后自动重连
└── 性能恢复
```

## 安全设计

### API Key 安全

```
.env 文件 (权限 600，仅 owner 可读)
├── BINANCE_API_KEY=xxx
├── BINANCE_API_SECRET=xxx
└── BINANCE_TESTNET=true

API Key 限制：
├── 只允许交易 (Spot Trading)
├── 禁止提币 (Withdraw)
├── IP 白名单 (可选)
└── 仅限 Testnet (初期)
```

### 服务隔离

```
trading-core:
├── 无需 API Key
├── 只读操作
└── 独立日志

strategy-service:
├── 无需 API Key
├── 只读 Redis + 写信号
└── 独立日志

trading-engine:
├── 需要 API Key
├── 读写操作
├── 独立日志
└── 独立用户运行 (非 root)
```

## 监控设计

### 关键指标

```
trading-core:
├── 行情采集延迟 (ms)
├── 数据写入 QPS
├── Redis 写入延迟
└── 连接状态

strategy-service:
├── 策略执行延迟 (ms)
├── 信号生成频率
├── Redis 读取延迟
└── WebSocket 连接数

trading-engine:
├── 信号处理延迟 (ms)
├── 风控检查延迟 (ms)
├── 下单延迟 (ms)
├── 成功率 (%)
├── 当前持仓价值
└── 未实现盈亏
```

### 告警规则

```
Critical (立即处理):
├── 交易执行失败
├── 风控熔断触发
├── 服务连续崩溃
└── API Key 无效

Warning (关注):
├── 下单延迟 > 1s
├── 风控规则频繁触发
├── 日亏损接近限制
└── 持仓接近上限

Info (记录):
├── 服务重启
├── 策略切换
├── 配置变更
└── 日交易汇总
```

## 总结

### 服务分离的优势

1. **安全性**：API Key 只在交易服务中
2. **稳定性**：数据采集和策略分析不受交易影响
3. **可维护性**：职责清晰，易于调试
4. **可扩展性**：可独立扩展、部署
5. **故障隔离**：单点故障不影响整体

### 关键约束

1. 信号只能从 strategy-service 发出
2. 风控计算必须用交易所实时数据
3. 信号执行必须经过完整校验链
